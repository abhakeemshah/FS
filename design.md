## 2. Database Entity Relationships

### Prisma Schema (`prisma/schema.prisma`)

```
┌─────────────────────────────────────────────────────────────┐
│                          User                                │
├─────────────────────────────────────────────────────────────┤
│ id (String, PK)      │ email (String, Unique)               │
│ password (String)    │ name (String?, Nullable)             │
│ role (String)        │ staffAccessMetaJson (String?, JSON)  │
│ createdAt (DateTime) │ updatedAt (DateTime)                 │
└─────────────────────────────────────────────────────────────┘
                              │
                              │ role: "admin" | "staff"
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                   CatalogSnapshot                            │
├─────────────────────────────────────────────────────────────┤
│ id (String, PK)      │ key (String, Unique)                 │
│ value (String?, Text)│ updatedAt (DateTime)                 │
└─────────────────────────────────────────────────────────────┘
                              │
                              │ Stores product catalog state
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    LedgerSnapshot                            │
├─────────────────────────────────────────────────────────────┤
│ id (String, PK)      │ key (String, Unique)                 │
│ value (String?, Text)│ updatedAt (DateTime)                 │
└─────────────────────────────────────────────────────────────┘
                              │
                              │ Stores sales/financial ledger state
                              ▼
```

### Model Descriptions

#### `User`
The central authentication entity. Each user has:
- **`id`**: CUID (Collision-less Unique ID) generated by Prisma
- **`email`**: Unique identifier used for login
- **`password`**: Bcrypt-hashed password (10 salt rounds)
- **`name`**: Optional display name
- **`role`**: Either `"admin"` or `"staff"` — determines access level
- **`staffAccessMetaJson`**: JSON string storing granular permission metadata for staff users (module access levels, allowed settings)
- **`createdAt` / `updatedAt`**: Automatic timestamps

#### `CatalogSnapshot`
Key-value store for product catalog state persistence:
- **`key`**: Unique identifier (e.g., `"fs-communication:catalog"`)
- **`value`**: JSON-serialized catalog data
- Used for caching product listings, categories, and inventory state

#### `LedgerSnapshot`
Key-value store for financial/sales ledger state:
- **`key`**: Unique identifier (e.g., `"fs-communication:sales-bills"`, `"fs-communication:dashboard-metrics"`)
- **`value`**: JSON-serialized ledger data
- Used for persisting sales records, invoices, and dashboard metrics

### Dual Storage Architecture

The application uses a **hybrid storage strategy**:

1. **Prisma/Database**: Primary storage for User accounts and session data
2. **File-based JSON Store** (`data/staff-accounts.json`): Fallback storage for staff accounts, enabling operation even when database connectivity is unavailable

This dual approach ensures resilience — if Prisma operations fail, the system falls back to file-based storage.

## 4. Authentication & Guardrails

### Authentication Flow

```
┌──────────────────────────────────────────────────────────────────────┐
│                         LOGIN FLOW                                    │
├──────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  1. User visits /login                                                │
│     └── Selects role (admin/staff)                                   │
│     └── Enters email + password                                      │
│                                                                       │
│  2. POST /api/auth/login { email, password, role }                   │
│     ├── Admin path:                                                   │
│     │   ├── Validate against ADMIN_EMAIL / ADMIN_PASSWORD env vars   │
│     │   └── Create JWT with role: "admin"                            │
│     │                                                                 │
│     └── Staff path:                                                   │
│         ├── Query Prisma User by email + role                        │
│         ├── Fallback: Query data/staff-accounts.json                 │
│         ├── Verify password with bcrypt.compare()                    │
│         └── Create JWT with role: "staff"                            │
│                                                                       │
│  3. Server sets cookies:                                              │
│     ├── auth-token: JWT (HttpOnly, Secure, SameSite=Lax)             │
│     └── auth-role: "admin" | "staff"                                 │
│                                                                       │
│  4. Client-side session storage:                                      │
│     ├── Admin: markAdminSessionActive() → localStorage               │
│     └── Staff: saveStaffSession() → cookie + localStorage            │
│                                                                       │
│  5. Redirect:                                                         │
│     ├── Admin → /access/admin/dashboard                              │
│     └── Staff → /access/staff/dashboard                              │
│                                                                       │
└──────────────────────────────────────────────────────────────────────┘
```

### Middleware Protection (`middleware.ts`)

The Next.js middleware intercepts requests to `/login/admin/*` and `/login/staff/*`:

```typescript
// middleware.ts logic:
1. Extract auth-token cookie
2. Decode JWT payload (without cryptographic verification — done in middleware for performance)
3. Check role from JWT payload
4. For /login/admin/* routes: require role === 'admin'
5. For /login/staff/* routes: require role === 'staff' OR valid staff session cookie
6. Redirect unauthorized users to /login
```

### `src/lib/staff-auth.ts` — Client-Side Auth Utilities

This module provides the complete client-side authentication API:

#### Storage Keys
| Key | Purpose |
|-----|---------|
| `fs-communication:staff-accounts` | Local staff account list (for offline auth) |
| `fs-communication:staff-session` | Current staff session data |
| `fs-communication:staff-session-active` | Session existence cookie |
| `fs-communication:admin-session` | Admin session timestamp |
| `fs-communication:staff-access-meta` | Permission metadata map |

#### Permission System
Staff users have granular permissions per module:

```typescript
type StaffAccessLevel = 'none' | 'view' | 'edit';

type StaffAccessMeta = {
  role: 'cashier' | 'sales' | 'inventory' | 'supervisor';
  status: 'active' | 'suspended';
  permissions: Record<StaffModuleKey, StaffAccessLevel>;
  allowedSettings: StaffSettingKey[];
  lastUpdatedAt: string;
};
```

Modules: `dashboard`, `sales`, `products`, `purchases`, `payments`, `parties`, `reports`, `settings`

#### Key Functions
| Function | Purpose |
|----------|---------|
| `authenticateStaff(username, password)` | Local password check against stored accounts |
| `saveStaffSession(account)` | Persist session to cookie + localStorage |
| `readStaffSession()` | Retrieve current session |
| `clearStaffSession()` | Logout staff user |
| `authenticateAdmin(email, password)` | Synchronous admin auth via XHR (dev only) |
| `saveAdminSession()` | Mark admin session active |
| `hasAdminSession()` | Check if admin session is fresh (<24h) |
| `getCurrentStaffModuleAccess(moduleKey)` | Get permission level for a module |
| `canCurrentStaffAccessModule(moduleKey, requiredLevel)` | Permission check |
| `fetchStaffAccessMetaById(staffId)` | Fetch permissions from server |
| `writeStaffAccessMetaMap(value)` | Update permissions (syncs to server) |

### Server-Side Auth (`src/lib/auth.ts`)

| Function | Purpose |
|----------|---------|
| `hashPassword(password)` | Bcrypt hash with 10 salt rounds |
| `verifyPassword(password, hash)` | Bcrypt comparison |
| `createAuthToken(payload)` | Sign JWT with HS256, 24h expiry |
| `verifyAuthToken(token)` | Verify and decode JWT |

### JWT Configuration (`src/lib/jwt.ts`)

- **Algorithm**: HS256
- **Secret**: `JWT_SECRET` env var (required in production; insecure default in dev)
- **Expiration**: 24 hours
- **Payload**: `{ id, email, role, iat, exp }`
